Input/Output: I/O Systems

Managing external devices. Polling, Interrupts, DMA, and the Kernel I/O Subsystem.

Port-Mapped I/O Polling Interrupts DMA Blocking/Non-blocking

Hardware Interface

A typical I/O device has a Port (connection point) and a Bus (daisy chain or shared access).
Device Controller: Electronics that operate the port/device. Has registers for data and control.

Memory-Mapped I/O Device registers are mapped to main memory addresses.
Access: Standard load/store instructions (`MOV`, `LD`).
Example: Video memory.
Port-Mapped I/O Uses special I/O instructions (`IN`, `OUT`) to access separate I/O address space.
Example: Early x86 architecture.

Communication Methods

How does the CPU talk to the device?

1. Polling (Busy Wait)

CPU repeatedly checks the status register: "Are you ready? Are you ready?".
Pros: Simple. Fast if device is fast.
Cons: Wastes CPU cycles if device is slow.

while (*status_reg == BUSY); // Spin loop *data_reg = byte_to_write; *command_reg = GO;

2. Interrupt-Driven I/O

CPU issues command and goes to do other work.
When device is done, it raises an Interrupt Request Line.
CPU stops, saves state, runs Interrupt Handler, restores state.
Benefit: CPU not tied up waiting.

3. Direct Memory Access (DMA)

Used for high-speed devices (Disks, Network) to avoid interrupting CPU for every byte.
How: CPU programs DMA controller (Source, Dest, Count). DMA transfers block directly to memory.
Result: Only one interrupt per block.

Kernel I/O Subsystem

The kernel provides generic services to hide hardware complexity.

I/O Scheduling Reordering requests (queueing) to optimize performance (e.g., disk elevator).
Buffering Store data in memory while transferring. Handles speed mismatch (modem vs SSD) and data size mismatch.
Caching Holding copies of data for faster access. (Buffer = copy, Cache = fast copy).
Spooling Holding output for a device that can only serve one request at a time (e.g., Printer).

Blocking vs Non-Blocking

Blocking I/O Process suspended until I/O completed. Easy to use/understand.
Non-Blocking I/O Call returns quickly with data count read (maybe 0). Process keeps running. Used in UIs/Video games.
Asynchronous I/O Process runs while I/O executes. Signal tells process when I/O is done. Hard to program.

Life Cycle of a Request

  1. User Process: Issues read() system call.
  2. Kernel: Checks parameters. Checks if data in cache. If not, requests device driver.
  3. Device Driver: Issues commands to device controller registers. Blocks process.
  4. Device Controller: Operates hardware. Transfers data. Generates Interrupt when done.
  5. Interrupt Handler: Saves data, signals driver.
  6. Kernel: Moves data to user space. Wakes up process.
  7. User Process: read() returns.

The Exam Vault

Professor's Secrets & Trap Avoidance

TRAP: Interrupt Overhead

Interrupts are good but have overhead (Context switch, Pipeline flush).
For very high-speed networks (e.g., 10Gbps), interrupts happen too often ("Livelock").
Solution: Hybrid approach (Switch to Polling under high load).

TRAP: Double Buffering

Often used in graphics/video. While one buffer is being displayed/written, the other is being filled. This decouples the producer and consumer rates.

SECRET: DMA & Caches

DMA writes directly to Main Memory, bypassing the CPU Cache. This creates a Cache Coherency problem (CPU reads stale data from cache).
Fix: OS/Hardware must invalidate cache lines affected by DMA.

KEY CONCEPT: Vectored Interrupt

Instead of a single "Interrupt" line where the CPU must poll every device to find who rang the bell, modern CPUs use an Interrupt Vector Table. The device sends an ID (Vector #), and CPU jumps directly to that device's specific handler.
