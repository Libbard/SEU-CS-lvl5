Design: Database Design

Transforming conceptual models (ERD) into a physical database schema. Normalization, Relations, and Physical File Organizations.

Logical vs Physical Relational Model Normalization (1NF, 2NF, 3NF) Indexing File Hashing

Design Process Steps

1. Logical Database Modeling

Describes data using a notation that corresponds to a data organization used by a DBMS (e.g., Relational Tables).

  • Transform ERD into Relations.
  • Normalization (to remove redundancy).
  • Independent of specific hardware.

2. Physical Database Design

Prescribing the technical specifications for data stored in computer memory.

  • File organization (Sequential, Indexed).
  • Hardware/OS choices.
  • Performance tuning.

The Relational Model

Data represented as a set of related tables (Relations). A Relation is a named, two-dimensional table of data.

Term Description
Primary Key An attribute that uniquely identifies each row. (e.g., StudentID).
Foreign Key An attribute in a relation that serves as the Primary Key of another relation. Links tables together.
Composite Key A primary key that consists of more than one attribute.

Normalization

The process of converting complex data structures into simple, stable data structures. It removes redundancy and prevents anomalies.

1

First Normal Form (1NF)

Rule: No multi-valued attributes. Every cell must hold a single value (Atomic).
Action: Create new rows or tables to handle multiple values.

2

Second Normal Form (2NF)

Rule: 1NF + No Partial Functional Dependencies. Every non-key attribute must depend on the whole primary key.
Action: Split tables if a field depends on only part of a Composite Key.

3

Third Normal Form (3NF)

Rule: 2NF + No Transitive Dependencies. Non-key attributes must not depend on other non-key attributes.
Action: Move transitive fields to their own lookup tables.

Physical File Organization

1. Sequential

Rows stored in sequence (e.g., by ID).
Pros: Fast for full scans.
Cons: Slow for random access.

2. Indexed

Uses an Index file (like a book index) to point to data locations.
Pros: Fast random access.
Cons: Storage overhead for indexes.

3. Hashed

Address is calculated from Key using an algorithm.
Pros: Very fast random access.
Cons: Not good for sequential scanning.

The Exam Vault

Professor's Secrets & Trap Avoidance

TRAP: 2NF vs 3NF

2NF Issue: Dependency on *part* of the Primary Key (Partial Dependency). Only happens with Composite Keys. 3NF Issue: Dependency on a *non-key* attribute (Transitive Dependency). If the PK is a single attribute, you are automatically in 2NF!

TRAP: Referential Integrity

"Can a Foreign Key be NULL?"
Yes (usually), unless it's part of the Primary Key. "Can a Primary Key be NULL?"
NEVER (Entity Integrity Rule).

SECRET: Transforming M:N

If you see a Many-to-Many (M:N) relationship in an ERD, you MUST create a new relation (table) for it in the Relational Model. The Primary Key of this new table is a composite key of the two original PKs.

KEY CONCEPT: Denormalization

Normalization optimizes for storage and update speed (no anomalies). Denormalization (adding redundancy back) optimizes for read speed (fewer joins). This is a physical design decision.
