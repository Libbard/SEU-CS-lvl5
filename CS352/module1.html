Analysis vs. Design

System Analysis

"The What"

The process of studying a procedure or business to identify its goals and purposes and create systems and procedures that will efficiently achieve them.

  • Understanding current problems.
  • Gathering requirements.
  • Specifying what the system should do.

System Design

"The How"

The process of defining the architecture, components, modules, interfaces, and data for a system to satisfy specified requirements.

  • Creating blueprints (UML).
  • Designing Database schemas.
  • Specifying how the system will be built.

Modern Methodologies

Agile Methodologies

A reaction to rigid, document-heavy methods. Agile prioritizes individuals, interactions, and working software over strict processes.

eXtreme Programming (XP)

  • • Short cycles & incremental planning.
  • • Pair Programming: Two devs, one screen.
  • • Automated testing is core.
  • • Heavy client involvement.

Scrum

  • • Designed for high chaos/flux.
  • • Sprints: 2-4 week work units.
  • • Product Backlog: List of all desired features.
  • • Daily Standups (15 min meetings).

Object-Oriented Analysis & Design (OOAD)

Modeling systems as collections of objects (combining data and behavior) rather than separating data from logic. Commonly implemented via RUP (Rational Unified Process).

Where does Software Come From?

1. Outsourcing

Hiring external firms to build/run systems.

  • Cost-effective, Focus on core business.
  • Loss of control, Security risks.

2. Off-the-Shelf

Buying pre-packaged software (e.g., Microsoft Office, SAP).

  • Fast deployment, Standard.
  • May not fit specific needs perfectly.

3. Enterprise (ERP)

Integrated systems for all biz functions (HR, Finance, Sales).

  • Single data source, Process integration.
  • Extremely complex & expensive implementation.

4. Cloud / SaaS

Renting software over the internet (e.g., Salesforce, Google Docs).

  • Low upfront cost, Scalable.
  • Data ownership/security concerns.

5. Open Source

Code is free to use/modify (e.g., Linux, MySQL, Firefox).

  • Free license, Community driven.
  • Support can be costly/inconsistent.

6. In-House

Building it yourself from scratch.

  • Perfect fit, Competitive advantage.
  • Highest cost, Staffing burden.

Software Reuse

Why reinvent the wheel? Reuse increases productivity and quality. However, it requires a culture shift.

Approach Reuse Level Cost Policy
Ad hoc None to Low Low Informal. "Use it if you find it." No enforcement.
Facilitated Low Low Developers encouraged. Some tools available.
Managed Moderate Moderate Mandated policies. Established processes for sharing.
Designed High High Code is written specifically for reuse from the start. Corporate "Reuse Office".

The Exam Vault

Professor's Secrets & Trap Avoidance

TRAP: Open Source Cost

"Open Source is free."
FALSE. The license might be free, but the Total Cost of Ownership (TCO) can be high due to implementation costs, lack of support, and need for internal expertise to maintain it.

TRAP: The Reuse Fallacy

"Ad hoc reuse saves money."
Usually false in the long run. Without management, ad hoc reuse leads to finding bad code, duplicating bugs, and high maintenance costs. Designed reuse has high initial cost but massive long-term savings.

SECRET: Analysis vs Design

If a question asks "Determining business requirements," it is Analysis.
If it asks "Specifying hardware or database schema," it is Design.
Think: Analysis = Problem Space. Design = Solution Space.

KEY CONCEPT: The Iron Triangle

In project management (and acquisition), you can't have it all. Fast, Cheap, Good — pick two. Off-the-shelf is Fast and Good, but maybe not cheap (licensing) or perfect fit. In-house is Good (fit) but Slow and Expensive.
